# 0006: Resolve Arm virt descriptions into modular firmware and launch plans

Status: accepted. Extends decisions 0004 and 0005; preserves the original v1 recipe as a regression contract.

Separate the platform configuration, backend capability checks, firmware components, application, and derived build/launch plans. The versioned input is platforms/arm-virt-a55.json. The Python resolver produces an immutable typed ResolvedPlatform after rejecting unsupported topology and boot state. The component registry selects AArch64 EL1 startup/services, a polled PL011 console, and the hello-world application. C sources live under firmware/ rather than inside Python string literals.

The same resolved configuration supplies CPU compiler flags, RAM/entry/stack linker settings, UART configuration and QEMU CPU/RAM/GIC options. UART base/size/clock/IRQ and RAM base remain constrained by the real Arm virt machine. Device entries are the firmware's required bindings, not a replacement inventory of every onboard QEMU device. No custom QEMU machine is generated by this change.

The desktop embeds the generator and trusted component assets so packaged generation does not depend on finding the repository's firmware directory. The new native command accepts bounded JSON description text, never executable paths, compiler flags, template paths or command strings. Python performs semantic validation at the execution boundary. Generated commands are retained in the trusted in-memory plan. Disk plan/platform manifests remain inspect-only and are never treated as executable configuration when rebuilding.

Software gains a platform-description editor. Successful application creates a fresh project; invalid input preserves the active project. Confirm before replacing unsaved source buffers. Rebuilds reuse saved sources, and regeneration reuses the active validated description. The captured architectural inventory remains a separate reference view and is explicitly not rewritten to match execution settings.

Preserve recipes/bare-metal/arm-virt-a55.json unchanged and preserve its original generator in scripts/legacy_bare_metal.py. The --recipe CLI/API path still generates the original bytes, checked against committed SHA-256 fixtures. The default CLI/desktop path uses modular generation. Test the original recipe boot, modular default boot and an alternate description, as well as Rust's generation/build/QMP/serial/source-workspace path.

Initial supported capabilities: QEMU 11.1.2 virt-11.1, one AArch64 A53/A55/A72 CPU, GICv2/v3, 16–2048 MiB contiguous RAM at the fixed base, PL011 UART0, EL1, and an ELF entry beyond the reserved first 2 MiB. Multicore startup, other console drivers, arbitrary device addition/relocation, other OSes, custom application packaging and custom machine backends remain future work. Users can edit main.c to supply application logic through the console/platform APIs.
